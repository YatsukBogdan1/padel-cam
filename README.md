# Padel Smart-Cam

Start and stop a Raspberry Pi camera at a padel court from a browser. The video goes to Cloudflare R2 and can be downloaded a few seconds after the recording stops.

## Status

This is a personal project in early-stage, active development. There is no company behind it and payments are not built.

I'm building it for club use, so the code has venues, a free-period gate and the word "customer" in comments. One camera is installed at a club as a free trial, and I'm offering free pilots to other clubs. This README makes no claims about usage.

This repo is a copy of a private repo with a fresh git history. Business documents, club-specific material and production config were removed, so IDs and hostnames are placeholders.

Most of the commits in the private repo were co-written with Claude Code. [`CLAUDE.md`](CLAUDE.md) is its instruction file, and also the most detailed architecture notes here.

### What works

- **Remote control:** start and stop from the admin UI. A QR page also lets players start their own match.
- **Upload while recording:** video reaches R2 through multipart upload during capture.
- **Network outages:** capture writes to the Pi's disk first, so an outage delays the footage instead of losing it.
- **Restarts and power cuts:** a restart costs a few seconds of video, and a power cut starts a new segment of the same match.
- **Housekeeping:** presence tracking, auto-stop at the end of a booked slot, retention, and cleanup of abandoned uploads.
- **Tests:** 127 Worker tests run inside `workerd` with real D1, R2 and Durable Object bindings, plus a fake camera over a real WebSocket.

The `e2e/` suite tests a real Pi and camera, including network loss, `kill -9` and `reboot -f`. It needs that hardware, so it was not re-run for this copy. An earlier version passed 10 of 10 scenarios in September 2026; scenarios added since then aren't covered by that figure.

### What doesn't work, or isn't finished

- **Payments:** not built. The `purchased` flag is always 0. Past a court's free period, the video is refused with a 402 and there is no way to pay.
- **Incident fixer:** `.github/workflows/fixer.yml` has never run end to end. Treat it as untested.
- **Admin UI gaps:** the backend records match segments, truncated recordings, warnings and camera health, but the admin UI shows none of them.
- **Fleet updates:** agents are deployed by `rsync` from a laptop, one Pi at a time. There is no update pipeline.
- **Device auth:** all Pis share one token.
- **Thumbnails:** generated by a script run by hand.
- **Frontend tests:** the admin SPA has no automated tests, only type checks.
- **Pi 5:** it has no hardware H.264 encoder, so 1080p is a software encode that overheated and throttled in testing. Throttling drops frames without raising an error. The Pi 4 has a hardware encoder.

## Architecture

```
 Browser (admin SPA, player pages)
        │  HTTPS
        ▼
 ┌─ Cloudflare Worker ──────────────────────────────┐
 │  HTTP API, player pages, cron sweeps             │
 │     │                  │                │        │
 │     ▼                  ▼                ▼        │
 │  Durable Object       D1               R2        │
 │  one per court        recordings,      video     │
 │  holds the camera     courts, venues   (multipart│
 │  WebSocket                              uploads) │
 └─────▲──────────────────────────────────▲─────────┘
       │ WebSocket: commands, heartbeats  │ HTTP PUT: video parts
       │ (the Pi dials out)               │
 ┌─────┴──────────────────────────────────┴─────────┐
 │  Raspberry Pi agent (Node, behind the venue NAT) │
 │  capture → on-disk spool → uploader              │
 └──────────────────────────────────────────────────┘
```

| Path | What it is |
|---|---|
| `admin/` | React 18, Vite, Tailwind and shadcn/ui admin SPA. It builds into `worker/public`. |
| `worker/` | Cloudflare Worker: API, server-rendered player pages (Portuguese and English), Durable Object, migrations, tests. |
| `agent/` | Camera agent, one Node process per Pi, plus provisioning scripts. |
| `e2e/` | End-to-end suite against a real Pi. |
| `terraform/` | The R2 bucket and D1 database only. Wrangler manages the Worker and its Durable Object migrations, because the Cloudflare provider has known bugs applying those migrations. |
| `enclosure/` | OpenSCAD source and STLs for the camera housing. |

### Why Durable Objects

A Pi sits behind the venue's NAT, so the cloud can't connect to it. The agent opens a WebSocket outward and waits for commands. A normal Worker request can't hold that socket for other requests to use, so something has to own it. `worker/src/court-camera.ts` is that owner, with one instance per court (`idFromName(courtId)`). That gives four things:

- **A stable address.** The camera's socket and an operator's "start" request both reach the same instance, which relays the command down the socket.
- **One camera per court.** A new connection closes the old one. Otherwise a reconnect could leave two agents attached, both uploading part N of the same multipart upload and overwriting each other's etags, and `complete` would then fail.
- **Real acknowledgements.** A socket silently dropped by NAT still accepts `send()`. The object waits up to 6 seconds for the agent's ack and returns a 409 if none arrives, so the UI doesn't show a recording light for a camera that never heard the command.
- **Cheap idle connections and a per-court timer.** The hibernation API means an idle connected camera isn't billed for duration. Each court's alarm stops a match at its end time, with a 5-minute cron as backup.

The object doesn't hold everything. D1 stores the recording and court rows, and video goes through ordinary Worker requests into R2, so a long upload doesn't pass through the object.

## Run it locally

You don't need a Cloudflare account, a Pi or a camera. Without `CAPTURE_CMD`, the agent generates about 5 MiB/s of filler bytes. The bytes are not a playable video, but they go through the whole start, upload, complete and download path against local D1 and R2.

Tested with Node 22 on macOS:

```bash
npm ci
npm run build
(cd worker && npm run migrate:local)

# Prompts for a password of at least 10 characters
node worker/scripts/create-admin.mjs --venue my-club --name "My Club" --email you@example.com --local
node worker/scripts/grant-super.mjs --email you@example.com --local

npm run dev                                 # terminal 1: http://127.0.0.1:8787
SPOOL_DIR=/tmp/padel-spool npm run agent    # terminal 2: a fake camera called court-1
```

Sign in, open `/super`, assign `court-1` to `my-club`, then start and stop a recording from the dashboard.

Checks:

```bash
npm run typecheck
npm test
```

## Deploying your own

These steps were not re-run for this copy. You need your own Cloudflare account and, for real video, a Pi with a camera.

1. Apply `terraform/` using `terraform.tfvars.example`, then put the `database_id` output into `worker/wrangler.toml` in place of the all-zeros placeholder.
2. Set `ALERT_TO` in `worker/wrangler.toml` and create the secrets listed in `worker/.dev.vars.example`. Without `DEVICE_TOKEN`, the camera routes have no authentication.
3. Run `npm run migrate:remote` from `worker/`, then `npm run deploy` from the repo root.
4. Provision each Pi: see [`agent/README.md`](agent/README.md) and `agent/deploy/.fleet.env.example`.

## Privacy

The system records video only: no `CAPTURE_CMD` opens a microphone. Filming people still carries legal duties, so check the rules where you install it.
